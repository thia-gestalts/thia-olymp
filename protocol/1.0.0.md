# Olymp protocol 1.0.0

Pin this document or the 1.0.0 SDK archive. The HTTP major prefix is `/v1`. A change to any required cryptographic or reconciliation behavior requires a new major protocol. All integers are JSON safe integers. Text is UTF-8. Standard base64 includes padding. Tuple contexts below mean compact JSON arrays encoded in UTF-8, without whitespace or a trailing newline. Treat account IDs as opaque, case-sensitive strings.

## Enrollment and unlock

The OPAQUE profile uses opaque-ke 4.0.1, Ristretto255 OPRF, TripleDH with Ristretto255 and SHA-512, and client Argon2id v19 with 19,456 KiB, two iterations and one lane. Use the library's default client/server identities and empty context. The credential identifier is the UTF-8 normalized login name (trim, ASCII lowercase, 1–64 characters from a–z, 0–9, dot, underscore and hyphen). Password bytes are exact UTF-8. All OPAQUE messages use the library serialization in standard base64. Challenges are single use and expire after 120 seconds.

| POST to /v1 | JSON request | Successful response |
|---|---|---|
| signup/start | name, message (RegistrationRequest) | id, challenge, message (RegistrationResponse) |
| signup/finish | challenge, message (RegistrationUpload), wrapped | 204 |
| login/start | name, message (CredentialRequest) | challenge, message (CredentialResponse) |
| login/finish | challenge, message (CredentialFinalization), device (1–120 UTF-8 bytes, nonblank app/device label) | account {id,name,generation}, token, wrapped |
| logout | authenticated, empty body | 204, revokes the presented token |

At registration generate a random 32-byte base root on the client. Use HKDF-SHA256 on the registration export key (empty salt, UTF-8 info `thia-personal-key-wrap-v1`) to derive a 32-byte AES key. Encrypt the root with AES-256-GCM, random 12-byte IV, 16-byte tag and AAD `["thia-server-unlock",1,id,0]`. Send `wrapped = base64(IV || ciphertext || tag)`. Complete login after signup. Use the login export key and returned generation in the same derivation and AAD to unwrap. Each device gets the same root and its own 30-day bearer session. The OPAQUE server setup, credential record and wrapped root must survive service restarts.

Send `Authorization: Bearer <token>` and `X-Olymp-Account: <account.id>` on all data and device requests. Logout needs just the bearer. Use HTTPS outside loopback. Browser apps use a same-origin reverse proxy for /v1, native hosts can call directly. The service does not log bodies. The service sees names, app/device labels, revisions, sizes, timing, session expiry, chunk membership and client-reported confirmation.

## Encrypted data

Derive the 32-byte content key by HKDF-SHA256 over the base root, empty salt, UTF-8 info `olymp-content-v1`. Use libsodium XChaCha20-Poly1305-IETF with a fresh random 24-byte nonce per encryption. Wire bytes are nonce || ciphertext || 16-byte tag.

Split each attachment in order into at most 262,144 plaintext bytes per chunk. A zero-length attachment is an empty list. AAD is `["olymp",1,id,"chunk"]`. The reference is lowercase hexadecimal SHA-256 of the **complete encrypted chunk**. Persist the actual encrypted bytes alongside the record before acknowledging a local commit. Reuse those exact bytes and IDs on retry. File order and chunk order matter. Encrypt the UTF-8 JSON manifest with AAD `["olymp",1,id,"manifest",nextRevision]`. Encode this envelope in standard base64.

| Endpoint | Contract |
|---|---|
| GET /v1/base | Returns {revision,envelope}. A missing base is {revision:0,envelope:null}. |
| POST /v1/missing | Takes a JSON array of chunk IDs, returns the subset absent in this account. |
| PUT /v1/chunks/{id} | Raw encrypted bytes. Digest-checked idempotent staging. Returns 204. |
| GET /v1/chunks/{id} | Raw encrypted bytes or 404. Verify digest and AEAD before accepting. |
| PUT /v1/base | JSON {revision,envelope,chunks}. Supply the **expected current revision**, encrypt for revision+1 and list the complete unique set of live references. Checks revision and chunk presence in one transaction. Returns new revision as a JSON number. |
| POST /v1/confirm | JSON {revision}. Records a durable client's acknowledgement only if the service still has this revision. Returns 204. |
| GET /v1/devices | JSON array of {device,confirmed}. One row per unexpired session. confirmed is null until first acknowledgement. |

401 requires sign-in. 403 indicates scope mismatch. 409 on publication or confirmation requires pulling and reconciling again. 413 means the request or account quota was exceeded. 429 indicates an auth rate limit. On transport errors retry from a new read. Staged or dereferenced chunks may be collected after 24 hours. The default chunk quota is 256 MiB per account including staging. The base publication body has a 4 MiB limit. Clients must keep pending work through every failure. An unauthorized or incomplete response never instructs a client to empty its replica.

## Record identity and reconciliation

The decrypted manifest is `{"heads":[],"removed":[]}` initially. A head has the form

```json
{"key":"example/note/123","id":"e25c8aeb-ab3a-4614-a5ac-66dd1aedc7a4","value":{"kind":"any","text":"hello"},"files":[],"deleted":false}
```

The logical record key belongs to the application. For events use a stable event ID in the key. For name-keyed references use an agreed namespace and canonical spelling across apps. Olymp compares key strings exactly. A new **operation** has a fresh random UUID, independent of its record key. An operation's contents are immutable. Values use interoperable JSON (use strings for large integers or exact decimals). `files` is the ordered list of attachments, each an ordered list of chunk IDs. Every referenced attachment must appear here, including those associated with unfamiliar payloads. Apps must preserve and relay every head, including all metadata, conflict branches and unrendered kinds.

1. For a replacement, add the IDs of observed heads of this key to `removed`, then create the new head. A deletion creates a head with deleted=true, null value and empty files. Keep only superseded IDs for causal knowledge, without their previous contents. Never prune these IDs in v1, since an offline writer may still refer to them.
2. Merge the two sets of removed IDs, union heads by operation ID, discard heads whose IDs are removed. Serialize heads by ascending ASCII operation ID and removed IDs unique and ASCII-sorted. Live heads for different logical keys merge independently. No timestamps participate.
3. Present one logical record per key. Equal concurrent JSON values, files and deletion flags coalesce in the view. Equality ignores JSON object member order. Preserve all contributing IDs. Concurrent edit/delete presents both alternatives. A delete without a competing live edit hides the record. Resolving a conflict supersedes the observed alternatives. With an editor that may remain open over incoming sync, pass the IDs from the editor's read.
4. For a single observed live JSON-object parent replaced by a JSON object, writers can include `edit:{from,fields,files}`. `from` is the parent operation ID, `fields` lists changed top-level fields including additions/removals, and the boolean `files` marks an attachment-list change. When all heads are live siblings with this metadata, compose their touched fields and attachment-list changes if all overlapping changes agree (absence is distinct from null). Different values for the same field, incompatible attachment edits, or ambiguous ancestry preserve whole versions. Writers can omit edit metadata and use whole-record conflict semantics. The storage manifest always retains every concurrent head until explicitly superseded.

## Completion and recovery

Hold an account-scoped local write lock, or atomically check the local version before committing. Fetch and authenticate the current manifest, merge all local changes, fetch missing local bytes, verify every live chunk and ensure the service holds them. Publish with revision compare-and-swap when needed. Persist the entire reconciled manifest including tombstones, all authenticated ciphertext chunks and the accepted revision. Only then confirm that revision with the service. All bytes must be readable and decryptable locally without network access.

**Fully synced at revision R** is a point-in-time statement. It requires those durable writes, no pending local change, and a successful confirmation of R. A local edit immediately makes the client pending. Interrupted uploads, incomplete downloads, unreadable storage, quota errors, lost acknowledgements or a failed confirmation cannot produce a new completion report. Another device can advance the base immediately afterward. The device list reports historical confirmation, never current online presence.

A returning client merges its durable local heads and tombstone IDs even when the service is empty. To restore a lost sync store, retain or restore the account database entries and matching OPAQUE setup, then reconnect a complete surviving client. It uploads every missing ciphertext chunk and publishes the merged manifest. A fresh client can then download it. To recover after device loss, credentials and an intact service base suffice. These operations restore current state, including replicated deletions. Historical revisions, trash, email, and recovery after losing credentials are outside v1.
